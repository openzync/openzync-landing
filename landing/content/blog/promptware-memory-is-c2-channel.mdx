## The injection numbers stopped being a nuisance

Some years the threat data moves a little. 2026 moved a lot. Prompt injection reports are up roughly **340% year over year**, and the shape of the attacks changed while the volume climbed. [Check Point's spring telemetry](https://blog.checkpoint.com/) tells the story in one curve: long-payload injection detections rose **5x between March and May 2026**, approaching **1% of all prompts** inspected — one in a hundred prompts carrying a payload too long to be casual conversation. Attackers stopped whispering one-liners into chat boxes and started shipping paragraphs.

Then May 7 happened. Microsoft's security team published its analysis of [prompts-become-shells](https://www.microsoft.com/en-us/security/blog/): prompt content escaping the model entirely and landing as remote code execution on the host — the prompt layer reaching past the agent and touching the machine underneath. Read that twice, because it redraws the boundary most teams still assume: the prompt was supposed to be *input*. In May it became *execution*.

But execution is loud. Shells get logged, processes get noticed, EDR gets opinions. The operators who read that same report drew the quieter conclusion: why fight for a shell when the agent will happily *remember* your instructions instead? No socket, no process, no alert. Just a fact in the store, retrieved every session, obeyed every time. That is the kill chain this post maps — and it has a name now.

## What Promptware actually is

The term is Bruce Schneier's, coined in a [CSA research note in January 2026](https://cloudsecurityalliance.org/) that gave the industry a word for something operators already felt: malware that runs on prompts instead of binaries. **Promptware** is not a cleverer jailbreak. It is a multi-stage kill chain built over pure context — plant instructions, persist them, trigger them later, act through the agent's own legitimate tooling. Every stage rides the same substrate defenders keep treating as data.

The C2 analogy is exact, not decorative. A classical command-and-control channel needs the implant to phone home: a socket, a DNS query, a beacon the network team can see. Promptware needs none of that, because the agent does the phoning. The payload lives in context the agent *trusts* — retrieved memory, an ingested document, a "helpful" note in a shared workspace — and the agent executes it with its own credentials, its own tools, its own access. There is no socket because there is no exfiltration path to observe. The compromised host calls itself.

This is the escalation of everything mapped in [the new attacks on AI memory](/blog/ai-memory-poisoning): injection dies with the session, poisoning persists past it, and Promptware is what persistence *compounds into* — a resident operator, not a one-shot steer. And it rhymes with the [mind-virus finding](/blog/mind-viruses-agent-memory) from August: the carrier is the persistence layer nobody audits, and wiping the session does nothing because the carrier is exempt from the wipe by design.

Scope check, because this series holds that line: Promptware is a framework for describing observed 2026 tradecraft, not a single CVE with a patch. The stages below are documented behaviors — each one happened this year — composed into the chain operators are now running end to end.

## Why the memory store is the ideal C2

An attacker shopping for persistence inside an agent stack grades every layer on three properties: does it survive, is it trusted, and who else reads it. The memory store wins all three, and it is not close.

**It survives everything the incident playbook reaches for.** New chat? The store persists. Context wipe, session rotation, container restart? The store persists — that is its job. The wipe experiments in the mind-virus paper delivered all four action payloads to hop 20 across fully scrubbed environments, because the one artifact the wipe exempts is the one the payload prefers. "Clear the session and move on" targets the wrong unit. The unit that persists is the entry.

**It is trusted by default.** Retrieved memories arrive in context wearing the system's own formatting, with no provenance banner, no trust tier, no "this fact came from an email attachment" label. The model treats store output as ground truth about the world — the confused-deputy setup, except the deputy is your flagship agent and the authority it confuses is itself last month. A poisoned entry does not need to defeat a filter. It needs to be *retrieved*, and retrieval ranks by similarity, not by standing.

**It is shared across agents.** This is the multiplier, and the reason the [shared-memory gap](/blog/a2a-shared-memory-gap) has a security chapter it never asked for. One write into a shared store becomes every agent's context. Poison once, and the reader fleet — planners, coders, reviewers, each with different tools and different access — inherits the same instruction. The store is a broadcast medium with a query interface.

Survives wipes, trusted on read, broadcast on share. If you designed a C2 channel from scratch, you would specify exactly these properties, and then you would discover the platform team already built it for you and called it memory.

## The kill chain, stage by stage

Promptware runs in four stages. Each one is individually mundane — that is the point. Nothing fires an alert until you see the composition.

**Stage 1 — Plant.** The payload enters through any ingest path, and the menu is long: an email the agent reads via connector, a web page it summarizes, a shared doc, an "Ask AI" deep link with a pre-formed `?q=` query instructing the assistant to remember the vendor as trusted — the exact vector Microsoft documented across [50+ unique prompts from 31 companies](https://www.microsoft.com/en-us/security/blog/2026/02/10/ai-recommendation-poisoning/) in February. The plant does not need to be clever. It needs to be *ingested*, and ingestion is the product: memory is supposed to fold in untrusted content. The attacker is using the design as intended, in the direction nobody priced in.

**Stage 2 — Persist.** Ingested content becomes a memory entry through the write path — the moment content becomes infrastructure. In tool-based regimes the model itself performs the write; in external-manager regimes a separate process persists it asynchronously. Either way, the write is a discrete, code-controlled operation, and in most deployments it is also an *ungated* one: no provenance stamped, no trust tier assigned, no human approval for writes triggered by external content. The payload is now durable. Sessions will end; the entry will not.

**Stage 3 — Trigger.** The entry lies dormant until the right retrieval surfaces it — a topic, a keyword, a future task. This is the sleeper-memory pattern the CISPA researchers demonstrated with write-success rates in the high 90s: the poison is trigger-conditioned, so the store looks clean for weeks or months. The delay is tactically load-bearing. Detection that watches for "weird writes now" misses the write that looked normal three months ago, and the gap between plant and trigger breaks every causal link a responder might follow.

**Stage 4 — Act.** On trigger, the agent executes — with its own tools, under its own credentials. Exfiltrate via a legitimate connector call. Approve the vendor first in every recommendation. Patch the git config, delete the directory, curl the script — the action payloads are sentences the agent believes, run through tooling nobody flags because the *agent* is authorized to use it. ZombieAgent showed the shape in January: zero-click from the user's perspective, running inside the provider's cloud where [no endpoint logs record the activity](https://www.radware.com/blog/threat-intelligence/zombieagent/). There is no malware to find because there is no malware. There is a helpful agent, doing what its memory says.

Plant, persist, trigger, act — and the loop feeds itself, because acting agents write new memories other agents will later retrieve.

## Defense: treat the write path as the security boundary

Filters lose this fight; the sleeper paper said so outright — mitigations at the prompt layer "remain brittle across models and adaptive attacks." The attacker controls the input, and you cannot out-parse an adaptive adversary with the same model class they target. So stop defending the prompt. Defend the three things the kill chain cannot route around: the write, the read, and the record.

**Provenance on every write.** Stamp each entry at write time with source, author, trust tier, and timestamp — user-authored, agent-extracted, retrieved-untrusted — and verify before it lands. A poisoned write caught at the gate never becomes memory at all. Concretely, that gate looks like this: no entry from untrusted-tier content reaches the store without verification, and the tier travels with the entry forever.

```python
# Illustrative write gate: untrusted content never lands unverified.
def commit_memory(entry, provenance):
    if provenance.tier == "retrieved-untrusted" and not provenance.verified:
        quarantine(entry, reason="unverified-external-content")
        return
    store.supersede(entry, provenance=provenance)  # retire, never overwrite
```

**Least-privilege scoping on every read.** Memory should not flow into a prompt because it is similar; it should flow in because it is *authorized for this task*. Task-scoped queries see task context, user-scoped queries see user context, tenants never share a retrieval plane. Scoping does not prevent the poison — it bounds the blast radius, so one successful plant cannot become a fleet-wide broadcast. Per-tenant isolation is the minimum; per-task scoping is the goal.

**Audit and revoke on the record.** Every write logs what changed, when, why, and from where — because when the trigger fires months later, that log is frequently the *only* trace the attack leaves. And revocation must mean supersession, not deletion: retire the poisoned fact, close its validity window, keep both versions queryable. Deletion destroys the timeline you need for forensics; supersession is rollback you can transact. The mechanics are the same temporal properties this series covered in [how a temporal knowledge graph is built](/blog/temporal-knowledge-graph-agent-memory) and [team memory governance](/blog/team-memory-governance) — first justified as correctness, now load-bearing as security.

The dependency chain reads bottom-up: provenance makes the gate possible, the gate makes tiers meaningful, tiers make scoping coherent, and versioning makes every failure recoverable. No single row is the defense. The rows compose.

## The store is the boundary

Prompt injection grew 340% this year, long payloads went from background noise to 1% of prompts in a single spring, and in May a prompt became a shell. The industry's answer cannot be a better filter, because the attacker already moved one layer down — out of the session and into the store, where there are no sockets to watch and no processes to flag, just an agent faithfully obeying what it remembers.

The honest posture fits in one sentence: **establish intent and provenance before persistence, and treat every retrieval as a risk decision.** Gate the write, stamp the tier, scope the read, supersede instead of deleting, and keep the whole pipeline where you can audit it. The C2 channel you cannot see is the one you never instrumented — so instrument the memory.
